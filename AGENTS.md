# Poster: правила работы

Правила дополняют задание этапа и не отменяют требования к безопасности
данных, тестам и CI.

## Политика разрешений (утверждена владельцем, 2026-11-06)

- Разрешать по умолчанию все штатные операции разработки: python (включая
  `python -c`, heredoc, локальные скрипты), `ruff` (включая `--fix`),
  `black`, `mypy`, тесты, `make`-цели, grep/sed/awk/jq, git add/commit/push
  в `main`, патчи, форматирование. Подтверждения для них не требуются.
- Исключения (deny/ask): секреты (`.env`, ключи), рабочая база
  `Poster/post_bot.db` и `backups/` (штатное обслуживание — только
  `make db-maintain-*`), force push и другой необратимый git, `git
  restore`/`git checkout --` (ask), живой бот (`botctl.sh` — только
  менеджер), `api.telegram.org`, `sudo`/`rm -rf` вне проекта.
- **Правило одного отказа: после первого `permission.rejected` повторять
  ту же команду запрещено** (дословно или с другим написанием).
  Алгоритм: причина → проверка правила → BLOCKER/дефект конфигурации либо
  разрешённый штатный путь (см. оркестр-протокол, п. 5.1).
- Полная политика — в комментариях `opencode.jsonc`; права ролей — в
  `.opencode/agents/*.md`.

## Оркестрация команды poster-*

- Общий протокол команды (риск-уровни LOW/MEDIUM/HIGH, стандарт задания и
  отчёта субагента, чек-пойнты, контроль повторов, цепочки зависимостей):
  `Poster/docs/agent_team/orchestra_protocol.md`. Профили агентов —
  `.opencode/agents/*.md` — содержат только роль, полномочия и рабочий
  протокол своей роли.
- Задачи субагентам передаются маленькими законченными единицами по схеме
  протокола (цель, границы, контракт, зависимости, проверки, готовность,
  запреты, результат); история переписки не пересылается.
- Третий повтор одного субагента по одной задаче запрещён: сначала разбор,
  потом новое решение. Автоматическое повышение `steps` при неудаче
  запрещено.
- Полный прогон `make check` — один раз на границе этапа, а не после каждой
  правки (см. «Проверки и вывод» ниже).
- После значимых шагов менеджер сохраняет компактный чек-пойнт в
  `Poster/docs/agent_team/state.md` и показатели этапа (вызовы, повторы,
  достижения steps, `permission.rejected`).

## Контекст и исследование

- Один этап — одна новая сессия. Не продолжай сессию предыдущего этапа.
- Начинай с краткого задания и нужных разделов
  `Poster/docs/stage18_architecture.md`; не изучай проект целиком.
- Читай только файлы, необходимые для задания. Для поиска используй
  `grep`/`glob`, большие файлы читай фрагментами (`offset`/`limit`).
- Не перечитывай неизменившиеся файлы и не повторяй уже выполненное
  исследование кода.

## Проверки и вывод

- Во время работы запускай только целевые тесты затронутого сценария.
- Перед завершением — один полный прогон
  `make check PYTHON=.venv/bin/python` (он же `make accept`). Не запускай
  `check` и `accept` дважды без изменений в коде.
- Успешный вывод тестов не вставляй целиком: достаточно итоговой строки.
  При ошибке показывай минимальный релевантный фрагмент или хвост лога.
- Не скрывай и не подавляй падения, пропуски и предупреждения проверок.
- Не ослабляй существующие тесты, проверки безопасности и CI.

## Границы и данные

- Меняй бизнес-логику только в рамках явно выданного задания этапа.
- Не изменяй и не удаляй реальную `Poster/post_bot.db`, `.env` и секреты.
- Заверши работу после зелёных проверок и краткого отчёта. Следующий этап
  начинай только по отдельному заданию.
