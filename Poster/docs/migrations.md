# Миграции схемы SQLite

Схема Poster создаётся **единой базовой версией 1.0.0** и развивается
механизмом версий в `migrations.py`. Внешних инструментов (Alembic) нет:
база — однофайловая SQLite, изменения схемы ручные, а вся служебная
информация умещается в журнале `schema_migrations`.

## 1. Базовая версия 1.0.0

`MIGRATION_1_0_0_BASELINE` создаёт с нуля всю схему релиза 1.0.0:

* 31 таблица (`users`, `places`, `place_names`, `bricks`, `templates`,
  `template_versions`, `template_snapshots`, `announcement_drafts`,
  `announcement_instances`, `brick_proposals`, `curator_entries`,
  `footer_entries`, `user_event_log`, `reports`, `user_states` и др.);
* 66 индексов, включая частичные уникальные (`ux_place_names_one_canonical`,
  `ux_place_admins_one_active`, `ux_admin_transfers_one_pending_place`,
  `ux_admin_transfers_token_hash`);
* CHECK/FK-ограничения и 45 триггеров (в том числе `no_delete` у неизменяемых
  журналов и проверки области видимости кирпичиков);
* журнал `schema_migrations` и каталог системных кирпичиков
  (`brick_types.SYSTEM_BRICKS`) с финальными описаниями.

История невыпущенных накопительных версий не поддерживается: база, созданная
промежуточными редакциями 0.x, считается несовместимой и должна быть
пересоздана штатной очисткой (`db_maintenance.py`, см. раздел 6).

## 2. Журнал `schema_migrations`

```sql
CREATE TABLE schema_migrations (
    version    INTEGER PRIMARY KEY,
    name       TEXT NOT NULL,
    checksum   TEXT NOT NULL,
    applied_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Версия — целое число, начиная с 1, строго непрерывное. `checksum` — SHA-256
нормализованного DDL версии (пробельные различия не считаются изменением,
любое смысловое изменение SQL — считается).

## 3. Устройство одной версии

```python
@dataclass(frozen=True)
class Migration:
    version: int
    name: str
    statements: tuple[str, ...]
    requires_tables: tuple[str, ...] = ()
```

`requires_tables` — таблицы, без которых шаги неприменимы. Если хотя бы одной
нет, шаги пропускаются, но версия всё равно фиксируется в журнале: повторный
запуск не должен пытаться снова. Базовая версия 1.0.0 создаёт всё с нуля,
поэтому список пуст.

`DEFAULT_MIGRATIONS` — кортеж всех версий по порядку; `LATEST_VERSION` —
последняя из них.

## 4. Что гарантирует механизм

`run_migrations(engine)` применяет недостающие версии и возвращает последнюю:

1. **Идемпотентность.** Уже записанная версия повторно не применяется.
2. **Одна транзакция.** `BEGIN IMMEDIATE` берётся до чтения журнала, все
   ожидающие версии идут одной транзакцией: сбой любой откатывает весь запуск,
   журнал не пополняется. DDL в SQLite транзакционен, поэтому полуприменённого
   состояния не бывает.
3. **Конкурентный запуск.** `BEGIN IMMEDIATE` + `busy_timeout` (30 с): второй
   процесс ждёт, затем видит уже применённые версии.
4. **Контроль целостности журнала.** Журнал обязан быть префиксом списка
   миграций кода с теми же контрольными суммами. Неизвестная (более новая)
   версия, разрыв или изменённая задним числом версия — `IncompatibleSchemaError`
   до любого DDL.
5. **Копия перед изменением.** Перед первым ожидающим DDL существующей
   непустой базы создаётся WAL-aware копия (раздел 5). Сбой копии отменяет
   миграцию: база остаётся нетронутой.
6. **Только файловая SQLite.** `:memory:` и другие СУБД отклоняются явно:
   приложение всегда работает с файлом; тесты используют временные файлы.

Исключения: `IncompatibleSchemaError` (журнал/схема несовместимы с кодом),
`BackupError` (копия невозможна — миграция не начиналась), `MigrationError`
(DDL не применён, база не изменена).

## 5. Резервная копия перед миграцией

`_has_pending_migrations` читает состояние без записи: пустой/новый файл копии
не требует, существующий читается только по журналу. Если есть что применять,
`create_database_backup` делает снимок:

* SQLite Backup API — видит зафиксированные данные в WAL (прямое копирование
  основного файла их бы потеряло);
* запись во временный файл рядом с базой, `PRAGMA integrity_check`, права
  `0600`, затем атомарный `os.replace`;
* имя: `<база>.backup-<UTC-метка>-p<pid>`;
* готовые копии никогда не удаляются и не перезаписываются; автоматической
  ротации нет.

## 6. Обслуживание базы после релиза

`db_maintenance.py` — единственный утверждённый путь очистки рабочей базы
(случайные shell-команды к ней запрещены):

```bash
make db-maintain-report          # целостность + проверенный WAL-бэкап + счётчики
make db-maintain-clean           # полный rebuild-цикл рабочей базы
make db-maintain-clean DB=/tmp/opencode/poster_maint_test.db
```

Цикл `clean` — «бэкап → bootstrap → верификация → атомарная замена»:
новая база создаётся штатным `init_db` в НОВОМ файле, проверяется
(`integrity_check`, журнал версий, каталог системных кирпичиков по кодам из
кода продукта, нулевые счётчики пользовательских таблиц) и только затем
атомарно подменяет рабочую. Требуется остановленная служба; при любой неудаче
рабочая база не изменяется, прежняя остаётся как `<база>.replaced-<метка>`.

## 7. Как добавлять миграции

1. **Никогда** не редактировать применённую миграцию и не удалять строки
   журнала.
2. Добавить в `migrations.py` новый
   `Migration(version=N, name=..., statements=(...))` в конец
   `DEFAULT_MIGRATIONS`; версия — ровно `предыдущая + 1`, без пропусков.
3. Только добавочные операции: `CREATE TABLE/INDEX`, `ALTER TABLE ADD COLUMN`.
   Разрушительные изменения — отдельный план восстановления.
4. Не использовать `executescript` (он ломает явную транзакционность);
   шаги должны быть идемпотентны по смыслу.
5. Добавить тесты:
   * новая база: версия применяется, таблицы и ограничения есть;
   * старая база: данные сохраняются;
   * первая ожидающая версия: копия создаётся до DDL;
   * повторный запуск: версия не применяется дважды;
   * сбой: журнал без версии, схема откатана;
   * сбой копии: миграция не начинается.
6. `make check` на Python 3.13 и 3.14.
7. Обновить этот документ, если меняется схема.

## 8. Безопасное применение к настоящей базе

Миграции применяются автоматически при старте бота (`init_db`). Приложение
само делает WAL-aware копию, но перед выкаткой всё равно нужен
эксплуатационный backup:

1. **Остановить бота** и убедиться, что процесс завершён.
2. Скопировать все файлы базы: `post_bot.db`, `post_bot.db-wal`,
   `post_bot.db-shm` (если есть). Предпочтительно —
   `sqlite3 post_bot.db ".backup 'post_bot.db.backup-ГГГГММДД'"`, затем
   `PRAGMA integrity_check`.
3. Развернуть новую версию кода.
4. Запустить бота (миграции применятся) **или** заранее, при остановленном
   боте, из каталога `Poster`:
   `DATABASE_URL="sqlite:////абсолютный/путь/post_bot.db" python -c "from database import init_db; init_db()"`.
5. Проверить лог миграций, наличие автоматической копии и
   `SELECT version, name FROM schema_migrations;`.
6. При ошибке: остановить бота, вернуть файлы копии на место, журнал вручную
   не править. Если миграция не начиналась из-за `BackupError`, база не
   изменена — устранить причину (место/права/диск) и повторить запуск.

Запрещено: применять миграции к настоящей базе из тестов; запускать тесты с
`DATABASE_URL` на рабочую базу; чистить рабочую базу вручную; запускать
polling ради проверки миграции.

## 9. Тесты механизма

* `tests/test_baseline_1_0_0.py` — семантическая идентичность базовой версии
  эталонной схеме: все объекты `sqlite_master`, колонки/типы/ограничения/FK,
  45 триггеров и каталог системных кирпичиков; повторный запуск, неизвестная
  версия, разрыв журнала, изменение применённой миграции, `:memory:` отказ и
  конкурентный запуск;
* `tests/test_db_maintenance_rebuild.py` — rebuild-цикл очистки: бэкап,
  bootstrap, верификация, атомарная замена и запрет работы с живой службой;
* `tests/test_stage19a_schema.py` и профильные `test_stage2*` — реальные
  UNIQUE/CHECK/FK/триггеры и сохранность данных при пересоздании схемы.

Полный прогон — `make check` (см. `README.md`, раздел «Проверки»).
