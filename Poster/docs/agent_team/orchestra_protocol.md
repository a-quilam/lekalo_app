# Оркестр Poster: общий протокол (v2, 2026-11-01)

Единый протокол для команды `poster-*`. Каждый профиль агента в
`.opencode/agents/*.md` описывает только свою роль, полномочия и
особенности; общие правила — здесь. При конфликте побеждает профиль агента
и прямое задание владельца.

## 1. Риск-уровни задач

Менеджер присваивает каждой задаче уровень и выбирает конвейер:

| Уровень | Примеры | Конвейер |
| --- | --- | --- |
| **LOW** | текст интерфейса, подпись кнопки, безопасная локальная компоновка | Developer → целевые тесты → Manager (Reviewer не нужен) |
| **MEDIUM** | новое поведение экрана, исправление обработчика, сценарии Telegram | контракт → Developer → Tester → Manager |
| **HIGH** | миграции БД, безопасность/авторизация, переходы состояний, шаблонный движок, доставка сообщений | контракт → Architect (при неопределённости) → Developer → Tester → Reviewer → Manager → полный CI |

Не снижать уровень ради экономии. Не поднимать до HIGH каждую кнопку.

## 2. Стандарт задания

Менеджер передаёт работу субагенту по схеме:

```
Цель: что изменить
Границы: компоненты и файлы
Контракт: проверяемое поведение (пользователь видит / нажимает / получает)
Зависимости: что может сломаться рядом
Проверки: какие тесты должны пройти
Готовность: когда остановиться и вернуться
Запреты: чего не трогать
Результат: формат отчёта
```

- Не пересылать весь пользовательский промпт, историю проекта или
  многостраничные спецификации. Вместо этого — путь к документу и раздел.
- Большая работа делится на самостоятельные компоненты **до** вызова
  субагента. Миграция или глобальный рефакторинг может затрагивать много
  файлов, но это надо явно обосновать в поле «Границы».

## 3. Формат ответа субагента (короткий протокол)

```
STATUS: done | blocked | failed
CHANGED: файлы
CHECKS: команда → итоговая строка
RISKS: реальные проблемы
NEXT: что осталось
LIMIT: достигнут ли steps (да/нет)
BLOCKER: конкретная причина, если есть
```

Architect и Reviewer используют аналогичный формат со своими полями
(см. их профили). Полные логи и перечисление всех прошедших тестов —
запрещены: только итоговая строка, при падении — минимальный фрагмент.

## 4. Чек-пойнт этапа

После каждого значимого шага менеджер фиксирует в
`Poster/docs/agent_team/state.md` компактный блок:

- что готово;
- какие файлы изменены;
- какой HEAD (короткий hash);
- какие тесты пройдены (итоговые строки);
- что осталось;
- какие решения нельзя менять;
- найденные проблемы.

Чек-пойнт — короткий и самодостаточный: продолжение задачи начинается с
чтения чек-пойнта и `git diff`, а не всего репозитория. Полную историю
прошлых релизов не переписываем и многостраничные логи не копируем.

## 5. Контроль повторов и разрастания

### 5.1. Правило одного отказа (обязательное, все роли)

**После первого `permission.rejected` повторять ту же команду запрещено** —
ни дословно, ни с другим написанием, ни через конвейер/heredoc/скрипт.

Алгоритм после отказа:

1. Получен отказ — зафиксируй запрещённую команду и причину.
2. Проверь действующее правило: `opencode.jsonc` (глобальные защиты) →
   профиль роли (`.opencode/agents/<роль>.md`).
3. Если операция должна быть разрешена по политике проекта — это дефект
   конфигурации: верни BLOCKER менеджеру / сообщи владельцу (править
   разрешения вправе Build или владелец).
4. Если операция действительно запрещена — выбери разрешённый штатный
   путь (например, вместо прямого доступа к рабочей базе — `make
   db-maintain-report`).
5. Если разрешённого пути нет — зафиксируй блокировку в отчёте и продолжай
   независимые задачи.

Обход действующих защитных запретов маскировкой команды (переименование,
обёртки, `python -c`, heredoc) запрещён. Одна и та же команда не повторяется
дважды — ни агентом, ни через повторный вызов субагента с тем же заданием.

### 5.2. Общий контроль разрастания

- **Третье продолжение одного субагента** по одной задаче — стоп:
  не перезапускать вслепую; выяснить, почему задача не влезает, разделить
  остаток или поменять подход.
- **Reviewer второй раз смотрит тот же diff** — только с новым конкретным
  вопросом или новым существенным diff.
- **Tester проверяет устаревший контракт** — сначала обновить контракт,
  потом тестировать.
- **Агент повторяет одно и то же без прогресса** — прекратить вызовы,
  переключиться на ручное решение или вопрос владельцу.
- Достигнутый `steps` — не повод автоматически поднимать лимит: сначала
  уменьшить задачу или разделить её.
- Обнаруженная вне задачи проблема → отдельная находка менеджеру, а не
  самовольный рефакторинг.

## 6. Зависимости между компонентами

Перед запуском Developer менеджер устно отвечает на четыре вопроса:

1. Какие компоненты затрагивает задача?
2. Кто потребляет изменённые данные?
3. Какие контракты могут измениться?
4. Какой минимальный интеграционный тест нужен?

Ключевые цепочки Poster (изменение одного звена → проверить инварианты
остальных):

- `template → compiler → draft → live preview → delivery`
- `Telegram entities → stored values → render → edit`
- `callback → conversation state → persistence → navigation`
- `place → permissions → template → deep link`

Это правила рассуждения, а не графовый фреймворк: никакой дополнительной
базы знаний не создаётся.

## 7. Тестирование до кода

Для серьёзного бага или нового UX-сценария менеджер может сначала поручить
Tester короткий воспроизводящий тест → Developer исправляет реализацию →
Tester независимо проверяет. Для простой правки текста тройной цикл не
устраивается (достаточно LOW-конвейера).

Tester проверяет **пользовательское требование**, а не то, что случайно
реализовал Developer: точный текст, форматирование, inline-кнопки,
callback_data, порядок сообщений, message_id, переходы, сохранение ввода,
повторный callback, сбой и восстановление — через существующий FakeBot.

## 8. Git worktrees

Изолированная параллельная работа — только когда задачи действительно
независимы, не пересекаются по ключевым файлам, а экономия времени
оправдывает координацию интеграции. Автоматически worktree для каждого
субагента не создаётся. Интеграцию и общий результат проверяет менеджер.

## 9. Учёт эффективности этапа

В конце этапа менеджер фиксирует в чек-пойнте (если данные доступны):

- время начала/завершения;
- число вызовов Developer/Tester/Reviewer/Architect;
- число достижений steps;
- число повторов и повторных ревизий;
- число `permission.rejected`;
- найденные дефекты;
- завершённые пользовательские требования.

Стоимость: у менеджера нет доступа к точному балансу RouterAI; нулевой
`cost` в OpenCode не считать стоимостью. Денежных жёстких лимитов нет —
только контроль числа вызовов и повторов.

## 10. Прогон тестов

- В работе — только целевые тесты затронутого сценария.
- Полный `make check PYTHON=.venv/bin/python` — один раз на границе этапа,
  перед релизом и при высоком риске регрессии. Не после каждой мелкой правки.
- Не запускать `check` и `accept` дважды без изменений кода.

## 11. Обслуживание тестовой БД после релиза

Утверждено владельцем: после каждого релиза **до первого публичного
выпуска Poster** тестовые данные очищаются. Операция уже согласована —
менеджер **не запрашивает повторного согласия** на неё.

Порядок (выполняет менеджер самостоятельно, штатный механизм
`Poster/db_maintenance.py`, запуск из каталога `Poster`):

1. `make db-maintain-clean` — полный цикл:
   проверка целостности базы → согласованный WAL-бэкап (SQLite Backup API,
   проверка копии) → очистка тестовых данных (системные объекты и
   superadmin-конфигурация сохраняются) → smoke-запуск `init_db` как
   повторная проверка результата;
2. результат зафиксировать в чек-пойнте (п. 4): путь бэкапа, число
   удалённых строк, итог повторной проверки.

Гарантии механизма:

- очистка невозможна без проверенного бэкапа этой же базы (контроль
  внутри `db_maintenance.py`);
- запись идёт в транзакции `BEGIN IMMEDIATE`: параллельная запись бота
  или другой транзакции не портится — при занятой базе обслуживание
  прерывается;
- разрешение на `make db-maintain-clean*` выдано менеджеру (и тестировщику
  с `DB=/tmp/...` — для проверки обслуживания на изолированной тестовой
  базе); developer, reviewer и architect право очистки рабочей БД не имеют,
  отчёт `make db-maintain-report` доступен всем;
- произвольные shell-команды к рабочей базе (`sqlite3`, `rm`, `cp` к
  `post_bot.db`, `backups/`) запрещены всем агентам; временные тестовые
  базы в `/tmp` — свободны для Developer и Tester.

Проверка самого механизма — только на временной базе
(`make db-maintain-clean DB=/tmp/opencode/<имя>.db`).
