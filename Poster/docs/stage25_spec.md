# Poster 2.5 — техническое и продуктовое задание (утверждено владельцем, 2026-11-02)

> Единый источник требований для Poster 2.5. Субагентам читать разделы,
> указанные в задании. Целевая версия 2.5, текущая 2.4.1 (HEAD f335a88).
> Обратная совместимость со старыми тестовыми данными не требуется;
> публичного релиза ещё не было.

## ЧАСТЬ I. ОСНОВОПОЛАГАЮЩИЕ ПРИНЦИПЫ

### 1. Продуктовая философия

Poster — приложение внутри Telegram, а не бот, засоряющий чат.

1. Минимальное число экранов.
2. Минимальное число служебных сообщений.
3. Предсказуемое поведение кнопки «Назад».
4. Никаких промежуточных подтверждений без необходимости.
5. Сохранение введённых значений и контекста.
6. Компактные клавиатуры.
7. Немедленное обновление редактируемых данных.
8. Цельный пользовательский анонс.
9. Безопасное удаление только тех сообщений, которые действительно должны удаляться.
10. Автономная разработка без постоянных вопросов владельцу.

При противоречии между удобством реализации и утверждённым пользовательским поведением приоритет имеет пользовательское поведение.

### 2. Автономность

Запрещены бессмысленные вопросы владельцу («Продолжать?», «Можно ли исправить?», «Запустить тесты?» и т. п.). Обычные инженерные решения — самостоятельно. К владельцу — только принципиально новый продуктовый вопрос. Не обходить ограничения безопасности OpenCode и файловой системы.

### 3. Команда

Используется существующая оркестрация poster-*. Задачи — небольшие законченные единицы по протоколу. Лимиты steps и модели не менять без технической необходимости. Architect — для сложных изменений модели данных, Tester — для независимой проверки пользовательских сценариев.

### 4. Обратная совместимость

- legacy-обработчики не сохранять; старые callback, не используемые интерфейсом, удалять;
- прежние экраны, заменённые новыми, должны исчезнуть;
- временные обходные механизмы не остаются в архитектуре;
- сохраняются: права доступа, корректные конфигурации, работающие кирпичики системы, стандартные шаблоны, поддержка Telegram entities, штатное восстановление и обслуживание;
- `config/ui_texts.yaml` (включая правки владельца) сохранять и согласованно обновлять; каталог текстов целиком произвольно не перезаписывать.

## ЧАСТЬ II. ЕДИНЫЙ КОНТРАКТ TELEGRAM-СООБЩЕНИЙ (приоритет над частными реализациями)

### 5. Три типа сообщений

**5.1. Служебный экран**: главное меню, управление, списки, карточки, конструктор, редактор, формы ввода, справка, панель управления медиагруппой. Общее правило: **один актуальный служебный экран, редактируемый при переходах**. Не отправлять новое сообщение при каждом нажатии кнопки, если существующее можно отредактировать. При смене экрана — редактирование текста, подписи или клавиатуры. Исключение — когда API Telegram объективно не позволяет.

**5.2. Готовый анонс** — пользовательский результат: сформированный текст, форматирование, ссылки, фотографии. **Готовый анонс нельзя превращать в служебный экран.** Запрещено заменять текст анонса текстом редактора или меню. Готовый анонс сохраняется в чате при обычной навигации.

**5.3. Пользовательский ввод** — сообщения с данными (название, описание, адрес, ссылка, фрагмент шаблона, фото, значения полей). После успешного сохранения — удаляется, если Telegram позволяет. При ошибке сохранения/валидации — сохраняется. Не удалять данные пользователя до подтверждения успешной обработки.

### 6. Правила создания служебных сообщений

При каждом переходе проверять: есть ли актуальный служебный экран; можно ли обновить его; нужна ли отдельная отправка по техническим причинам; что будет с предыдущим экраном; не останутся ли две активные клавиатуры с одинаковыми действиями.

Предпочтительно: `Список → Карточка → Редактор → Карточка → Список` — внутри одного обновляемого сообщения.

Недопустимо: цепочка новых сообщений на каждый шаг. Дополнительные временные сообщения после завершения операции корректно очищаются.

### 7. Правила удаления сообщений

Удаление служебных сообщений, пользовательского ввода, активных экземпляров анонсов и записей БД — **разные операции**. Нельзя использовать универсальный cleanup по `draft_id`/`announcement_id` без учёта назначения сообщений.

**Разрешено**: удалять обработанный пользовательский ввод после успешного сохранения; ненужные временные редакторы; устаревшую временную панель медиагруппы; снимать клавиатуру с прежнего экземпляра анонса; заменять активный экземпляр при изменении структуры медиа — контролируемо и безопасно.

**Запрещено**: удалять исторический анонс при выходе в меню; удалять анонс при открытии его нового экземпляра; удалять старые фотографии вместе с временным редактором; удалять пользовательский ввод до успешного сохранения; удалять опубликованные экземпляры при очистке БД; удалять все связанные Telegram-сообщения при удалении логической записи.

**Защита от ошибок**: учитывать невозможность удаления конкретного сообщения, ограничения Telegram, потерю доступа, повторную обработку callback, перезапуск, частичный сетевой сбой. Отсутствие ошибки в локальной БД — не доказательство успеха Telegram API.

### 8. Кнопка «Назад»

«Назад» — возврат к **фактическому предыдущему экрану**, не в зашитый раздел. Сохранять: источник перехода, объект, площадку, страницу, поиск, фильтры, состояние редактора, контекст анонса. Открыл карточку с 3-й страницы поиска → «Назад» показывает ту же 3-ю страницу. Редактор готового анонса → «Назад» к управлению этим анонсом, не в меню. Не заменять «Назад» кнопкой «В меню». Не показывать ложный stale-alert для актуальных маршрутов.

## ЧАСТЬ III. ИНТЕРФЕЙС УПРАВЛЕНИЯ

### 9. Единый эмодзи кирпичиков

Заменить 🧱 на **🧩** во всех актуальных кнопках, заголовках, списках, действиях создания/редактирования, предложениях кирпичиков. Внутренние идентификаторы и коды кирпичиков не менять.

Индивидуальные эмодзи системных кирпичиков перед названиями (только оформление): 🏷 Название, 📅 Дата, 🕒 Время начала, 🕒 Время окончания, 📍 Место, 🔗 Ссылка места, 📝 Описание, ☎️ Контакт, 🗺 Адрес, 🌆 Город. Редактора эмодзи для пользовательских кирпичиков НЕ добавлять.

### 10. Компактное меню «Управление»

```
📍 Площадки
📝 Шаблоны | 🧩 Кирпичики
🛡 Администрирование
🏠 В меню
```

Кнопка администрирования — только тем, кому доступен раздел. «Шаблоны» и «Кирпичики» — в одной строке. Пустых кнопок не создавать.

## ЧАСТЬ IV. ПЛОЩАДКИ

### 11. Новый мастер создания площадки

Порядок: 1) Название — обязательно. 2) Город — обязательно. 3) Адрес — необязательно. 4) Ссылка — необязательно.

На обязательных этапах: ввести значение или вернуться назад. На необязательных: `◀️ Назад` | `⏭ Пропустить`. При первом пропуске поле остаётся пустым. При возвращении к заполненному полю «Пропустить» НЕ стирает ранее введённое значение; для изменения пользователь отправляет новое. После последнего этапа — сохранение без экрана подтверждения. Никаких фиктивных заглушек. URL и значения — действующими валидаторами. Новая площадка получает актуальный стандартный шаблон и базовые кирпичики. Последующее редактирование всех четырёх полей сохраняется.

### 12. Административная карточка площадки

**Одна полная карточка** без дублирующего меню.

```
✏️ Редактировать место | 📄 Шаблон
[🧩 Предложения кирпичиков | ⚔️ Конфликты кодов]  — динамическая строка
🧩 Кирпичики
👤 Назначить администратора / 👤 Управлять администратором
🔗 Ссылка для создания анонса
◀️ К списку мест | 🏠 В меню
```

Кнопки предложений и конфликтов показываются ТОЛЬКО при наличии соответствующих актуальных записей; оба есть — одна строка; один есть — только он. Не показывать пустые разделы с `(0)`. После обработки последнего предложения/конфликта — обновлять текущую клавиатуру. После поступления новой записи кнопка появляется при следующем актуальном отображении. Не создавать второй механизм назначения администраторов. Все права проверять на сервере.

### 13. Локальные кирпичики площадки

В `Площадка → Кирпичики` добавить кнопку `➕ Создать кирпичик` — открывает существующий конструктор. Создаваемый кирпичик: область `place`, сразу принадлежит площадке, не личный, не предложение, без согласования. Администратор площадки вправе создавать; суперадмин имеет все полномочия. После сохранения — возврат к списку кирпичиков той же площадки.

**Исправление дефекта**: «Назад» из раздела кирпичиков иногда выводит «Эта кнопка больше не работает. Откройте раздел администрирования заново». Восстановить корректный callback и переход в административную карточку текущей площадки. Проверить после перезапуска бота.

## ЧАСТЬ V. УНИВЕРСАЛЬНЫЕ СПИСКИ

### 14. Единая пагинация

Один переиспользуемый механизм для: площадок, шаблонов, кирпичиков, предложений, конфликтов, «Моих анонсов» и других длинных списков. Наличие кнопок удаления не отменяет пагинацию.

- **0–5 объектов**: весь список; без стрелок, номера страницы и служебных счётчиков.
- **6+ объектов**: 5 объектов на страницу; под списком одна строка `◀️ | 2/4 | ▶️`. Число страниц — по реальному количеству. На первой странице нет стрелки влево, на последней — вправо. Не вставлять декоративную пустую кнопку вместо отсутствующей стрелки. Индикатор `2/4` неактивен. В Bot API 10.3 есть поле `disabled` (DisabledButton) — проверить поддержку библиотекой; если не поддержана — безопасный no-op callback без изменения состояния и создания сообщения. Не менять библиотеку только ради индикатора.
- **Записи с удалением**: `Название | 🗑` — одна запись; пять записей максимум на страницу даже при десяти кнопках.
- **После изменения списка**: при удалении обновлять текущую страницу; если последняя страница исчезла — переход на новую последнюю; не оставлять пустые страницы с активными стрелками; список ≤5 объектов — без пагинации.

### 15. Контекст списков

Возврат восстанавливает: страницу, поисковый запрос, фильтры, порядок, родительский раздел. `Поиск → Страница 3 → Шаблон → Редактирование → Назад → Страница 3 того же поиска`. Не сбрасывать страницу на первую. Исправить дефекты `plm_back` и `tp_pick_back`. При рестарте использовать сохранившийся контекст, когда он доступен и валиден; если потерян — безопасно восстановить рабочий родительский экран без ложного stale-alert.

### 16. Выбор площадки при создании анонса

Вход `📝 Создать анонс` → сразу существующий выбор площадки с пагинацией. Под списком: `🔎 Найти площадку` | `➕ Новая площадка`; далее `📝 Создать по личному шаблону`; последняя строка `◀️ Назад`. Промежуточного экрана «Как хотите создать анонс?» НЕТ. Возврат из личных шаблонов — тот же список, поиск и страница. При создании новой площадки сохранять контекст исходного действия.

## ЧАСТЬ VI. СИСТЕМНЫЙ КИРПИЧИК ДАТЫ

### 17. Формат `[дата]`

Всегда **`ДД.ММ (дн)`**: две цифры дня, две цифры месяца, без года, две русские буквы дня недели в нижнем регистре, день недели соответствует дате. Примеры: `09.11 (пн)` — 9 ноября 2026; `10.11 (вт)` — 10 ноября 2026. Относится к рендеру системного кирпичика, не к произвольному тексту шаблона. Внутреннее хранение даты не менять. Проверить: личный шаблон, шаблон площадки, основной, расширенный, создание, повторное редактирование, открытие из «Мои анонсы». Не допускать повторного появления `09.11.2026` из другой ветки рендера.

## ЧАСТЬ VII. ЦЕЛЬНЫЙ ГОТОВЫЙ АНОНС

### 18. Убрать промежуточный экран «Анонс готов»

Сейчас после создания появляется `✅ Анонс готов` с кнопками `Изменить | В меню`. Экран удалить. После завершения конструктора пользователь сразу получает **сам готовый анонс с полноценным управлением** (актуальные действия существующего редактора: поля, доп. поля, фотографии, выход в меню). Не дублировать действия разными кнопками.

### 19. Цельность анонса — абсолютное требование

Нельзя искусственно отделять полный текст анонса от его фотографий. Если Telegram позволяет разместить текст в подписи фотографии или альбома — так и делать. Rich Message для анонсов запрещён.

### 20. Отправка без фотографий

Одно обычное сообщение `sendMessage`: полный текст, форматирование, ссылки, InlineKeyboardMarkup редактора. Без «Анонс готов», без отдельной панели, без прежнего служебного экрана конструктора. Очистка конструктора — только после успешной отправки анонса.

### 21. Отправка с одной фотографией

Одно сообщение `sendPhoto`: фото + весь текст caption + форматирование + ссылки + InlineKeyboardMarkup полного редактора. Фото, текст и кнопки — в одном Telegram-сообщении. Без второго служебного сообщения ради кнопок.

### 22. Отправка с несколькими фотографиями

Одна стандартная медиагруппа `sendMediaGroup`; весь текст — в caption первого элемента; остальные фото не дублируют текст. Это один альбом. Так как у `sendMediaGroup` нет общей inline-клавиатуры, разрешается **одно отдельное служебное сообщение с кнопками управления**: только управление, не дублирует текст, не является «Анонс готов», открывает действующие редакторы, связано с конкретным активным экземпляром, переиспользуется при переходах редактора, не создаёт новую панель на каждом нажатии.

**Категорически запрещён вариант «альбом + отдельное текстовое сообщение с полным анонсом».**

### 23. Ограничения длины

Photo caption — 1024 символа после обработки entities; sendMessage — своё ограничение. Проверять длину окончательного отрендеренного текста перед отправкой (не длину исходного HTML). Если не помещается: не отправлять неполный анонс; не обрезать; не отправлять фото отдельно; не использовать Rich Message; сохранить черновик, фото и значения; объяснить ограничение; предложить вернуться к редактированию текста; после исправления повторить отправку. Не создавать ложное состояние «опубликовано». Для медиагрупп учитывать допустимое количество фото и другие реальные ограничения Bot API.

### 24. Жизненный цикл конструктора после завершения

После успешной отправки: сохранить идентификаторы отправленных сообщений; зарегистрировать новый активный экземпляр; связать с логическим анонсом; закрыть состояние конструктора; удалить/закрыть ненужные временные служебные сообщения; удалить обработанный пользовательский ввод, где разрешено; оставить актуальное управление у анонса.

При ошибке отправки: не объявлять анонс готовым; сохранить черновик; не уничтожать конструктор; не терять фотографии; дать возможность исправить ошибку или повторить отправку. При частично выполненной отправке с неоднозначным ответом — безопасное восстановление без бесконтрольных дубликатов.

## ЧАСТЬ VIII. РЕДАКТИРОВАНИЕ ГОТОВОГО АНОНСА

### 25. Анонс никогда не превращается в редактор

При «Поля» анонс остаётся на месте. Открывается **временный служебный редактор**; исходный анонс самостоятелен.

### 26. Редактор для одного сообщения

Для анонсов без фото/с одним фото: кнопка редактирования у анонса → создание или переиспользование одного временного служебного экрана редактора → изменение значений → сохранение в БД → обновление активного экземпляра соответствующим Telegram API → редактор отражает актуальное состояние → «Назад» к управлению анонсом → ненужный временный экран удаляется. Не создавать отдельный редактор при каждом переходе между полями.

### 27. Редактор медиагруппы

Для анонса с несколькими фото — существующая отдельная панель управления. «Поля», «Фотографии» и другие действия: обновлять панель, показывать раздел, сохранять данные, обновлять подпись альбома, возвращать панель в основное состояние. Не отправлять новую панель поверх прежней. Не превращать альбом в служебный экран.

### 28. Редактирование активного экземпляра

Без фото — `editMessageText`. Одно фото — `editMessageCaption`, `editMessageMedia` когда требуется и поддерживается. Несколько фото — обновление caption нужного элемента медиагруппы, допустимые операции изменения медиа. Не пересоздавать сообщение при простом изменении текста, если Telegram позволяет отредактировать.

**Изменение количества фотографий** (0↔1↔несколько): если Telegram не позволяет изменить структуру непосредственно, допустима контролируемая замена **только активного экземпляра**: подготовить полный новый экземпляр → отправить → проверить результат → переключить активные идентификаторы → корректно закрыть старое управление → удалить заменённые сообщения прежней структуры только после успешного создания новой и когда удаление разрешено. Исторические экземпляры не трогать. При ошибке — возможность восстановления. Не допускать двух независимых активных редакторов.

## ЧАСТЬ IX. «МОИ АНОНСЫ» И ИСТОРИЧЕСКИЕ ЭКЗЕМПЛЯРЫ

### 29. Открытие готового анонса

Сейчас при выборе из истории бот показывает только служебное «Анонс готов». Исправить: при выборе готового анонса из «Мои анонсы» бот **всегда отправляет новый полноценный экземпляр** (полный текст, форматирование, гиперссылки, фотографии, управление). Не редактировать старый экземпляр вместо отправки нового. Не создавать новый логический анонс в БД.

### 30. Только один активный экземпляр

Один активный экземпляр с работающим управлением на логический анонс в чате. При повторном открытии: 1) отправить новый полноценный экземпляр; 2) убедиться в успешной отправке; 3) перевести предыдущий экземпляр в архивный статус; 4) убрать его inline-кнопки; 5) если предыдущий был медиагруппой — удалить его прежнюю временную панель, когда разрешено; 6) оставить его текст и фото в истории; 7) сделать новый экземпляр активным. Если отправка нового не удалась — не отключать управление прежнего.

### 31. Архивные экземпляры

Архивный экземпляр — неизменяемый снимок без кнопок: сохраняется в чате, сохраняет фото и текст, не обновляется при редактировании нового экземпляра, не получает активное меню, не становится редактором. Старые экземпляры — не источник новых редакторов и не запасной активный экземпляр.

### 32. Защита старых callback

Если Telegram не смог удалить старую клавиатуру, callback проверяет актуальность экземпляра: устойчивая привязка к `announcement_id`, `chat_id` и идентификатору/поколению активного экземпляра. Устаревший callback: не изменяет данные, не открывает старый редактор, не восстанавливает старую версию, не создаёт новый экземпляр, возвращает короткое пояснение через callback answer. Защита действует после перезапуска.

### 33. Удаление анонса из Poster

Удаление из списка — удаление логической записи и связанных пользовательских данных по действующим правилам. **Не означает удаление исторических сообщений Telegram.** Не удалять отправленные ранее анонсы из чата. Отключить управление, которое больше не имеет действительной записи. Не восстанавливать удалённый анонс старой кнопкой.

## ЧАСТЬ X. ФОТОГРАФИИ

### 34. Экран фотографий

В редакторе фотографий убрать `🏠 В меню`; вместо неё `◀️ Назад` — к управлению текущим анонсом.

### 35. Ноль фотографий

`📥 Добавить фото` + `◀️ Назад`. Никаких кнопок удаления.

### 36. Одна фотография

```
📥 Добавить фото | 🗑 Удалить фото
◀️ Назад
```

Не показывать «Удалить фото 1», «Удалить все фото».

### 37. Две и более фотографии

«Добавить фото»; кнопки удаления конкретных фото (по две в строке, если подписи позволяют); «Удалить все фото» отдельным действием с подтверждением; «Назад». После любого изменения пересчитывать клавиатуру. 2 → 1 — немедленная раскладка одной фотографии; удаление последней — раскладка нуля. Для длинных списков — компактное разбиение, без бесконечной клавиатуры. Не терять фотографии при неудачной операции Telegram.

## ЧАСТЬ XI. УСЛОВНЫЕ ЧАСТИ ШАБЛОНОВ

### 38. Зачем

Расширенный шаблон `[время_начала]–[время_окончания]` при заполненной цене, но пустом времени окончания даёт `19:00–`. Проблема касается тире, скобок, запятых, двоеточий, вводных слов, эмодзи, целых строк и абзацев. Универсальное автоудаление произвольной пунктуации запрещено.

### 39. Концепция

**Автор сам определяет, какую часть текста скрывать, если конкретный кирпичик пустой.** Шаблон остаётся обычным текстом. Никакого синтаксиса условий: `{{...}}`, `if`, XML, шаблонные выражения, языки программирования. В редакторе шаблона — отдельный раздел **«Условные части»**. Правила хранятся отдельно от текста шаблона.

### 40. Путь пользователя

`Шаблон → Условные части → Выбор кирпичика → Выбор фрагмента → Предпросмотр → Сохранить`.

**Шаг 1. Выбор кирпичика**: кирпичики, встречающиеся в тексте данного шаблона. Несколько вхождений одного кирпичика — выбор конкретного вхождения с показом окружающего текста.

**Шаг 2. Выбор скрываемого фрагмента**: «Выбери, какую часть текста скрывать, если этот кирпичик не заполнен». Понятные варианты: скрыть кирпичик вместе с соседним разделителем; скрыть целую строку; указать собственный фрагмент. Предложенный фрагмент не сохраняется автоматически — автор подтверждает выбор.

**Шаг 3. Собственный фрагмент**: точный фрагмент исходного текста, например `–[время_окончания]` или `💰 Цена: [цена]`. Проверки: фрагмент существует; включает выбранный кирпичик; найдено нужное вхождение; нет недопустимого пересечения с другим правилом. При неоднозначности — выбор нужного совпадения с контекстом. Не заставлять указывать смещения, индексы, идентификаторы диапазонов.

**Шаг 4. Предпросмотр**: «Кирпичик заполнен» и «Кирпичик пуст». Сохранение только после подтверждения.

**Шаг 5. Управление правилами**: посмотреть все; открыть конкретное; увидеть скрываемый фрагмент; изменить; удалить; вернуться в редактор шаблона. Без ненужных промежуточных экранов.

### 41. Модель условных частей

Правило привязано: к шаблону; к его версии или секции; к одному управляющему кирпичику; к одному конкретному текстовому фрагменту. Одна условная часть зависит от одного кирпичика. AND/OR/вложенные условия не нужны.

Кирпичик заполнен → фрагмент остаётся и отрисовывается с подставленным значением. Кирпичик пуст → весь фрагмент скрывается. Скрывается целая строка → удалить и лишний перевод строки, без ненужных пустых строк. Соседний текст не изменять. Эвристическую зачистку пунктуации вне авторского фрагмента не применять.

### 42. Обязательные примеры

- **А. Время окончания**: шаблон `[время_начала]–[время_окончания]`, правило `–[время_окончания]`. Пусто → `19:00`; заполнено → `19:00–22:00`.
- **Б. Цена**: шаблон `💰 Цена: [цена]`, правило `💰 Цена: [цена]`. Пусто → строка исчезает; заполнено → `💰 Цена: 500 ₽`.
- **В. Адрес**: шаблон `📍 [место] ([адрес])`, правило ` ([адрес])`. Пусто → `📍 РанДом Культуры`; заполнено → `📍 РанДом Культуры (Большой Николопесковский, 13)`.
- **Г. Независимые кирпичики**: цена заполнена, время окончания пусто → расширенный шаблон включён, но тире и пустое время не отображаются.
- **Д. Целый абзац**: правило охватывает самостоятельную строку/абзац → после скрытия нет лишнего пустого абзаца.
- **Е. Повторяющиеся фрагменты**: два одинаковых вхождения — автор выбирает конкретное; оба не удаляются без разрешения.

### 43. Простой и расширенный шаблоны

Сохранить правило выбора: нет заполненных доп. кирпичиков → простой; хотя бы один заполнен → расширенный; внутри расширенного условные части скрываются независимо; последнее доп. значение удалено → снова простой. **Переключение версии шаблона и видимость фрагмента — независимые механизмы.** Старый append-fallback не возвращать.

### 44. Редактирование и копирование шаблонов

Правила хранятся в БД и переживают перезапуск. Поддержка: личные шаблоны, шаблоны площадок, `content`, `extended_content`. Копирование простого шаблона в расширенный — действительные правила могут переноситься, но версии после копирования независимы. Не создавать общие изменяемые правила для двух версий.

При изменении исходного текста проверять актуальность правил: фрагмент остался однозначно тем же — правило сохраняется; изменён, удалён или неоднозначен — правило помечается как требующее перенастройки. Не применять устаревшее правило к случайному похожему месту. Не удалять пользовательское правило молча — показывать проблему и возможность исправления. Некорректное правило не разрушает весь редактор.

### 45. Сохранение Telegram-форматирования

Не допустить регрессию исправления 2.4.1. Сохранять: bold, italic, underline, strikethrough, spoiler, code/pre, гиперссылки, URL, кириллицу, эмодзи, корректные UTF-16-смещения, HTML-безопасность. Не определять фрагменты по случайным позициям в уже экранированном HTML. Операции скрытия — над логическим текстом и соответствующими сущностями форматирования.

## ЧАСТЬ XII. TELEGRAM RICH MESSAGE — СПРАВКА

### 46. Что такое Rich Message

Rich Message — официальный самостоятельный тип структурированного сообщения Bot API (10.1 от 11.06.2026; блоки в 10.2; интерактивность в 10.3). Обычный `sendMessage` с `parse_mode=HTML` — не Rich Message. Поддерживает: заголовки нескольких уровней, параграфы, списки, разделители, цитаты, таблицы, раскрываемые разделы, ссылки/якоря, блоки медиа, интерактивные элементы. Rich Message используется **исключительно для «Помощи»** и не является способом доставки анонсов.

### 47. Документация

Изучить перед кодом: https://core.telegram.org/bots/api , https://core.telegram.org/bots/api#sendrichmessage , https://core.telegram.org/bots/api#inputrichmessage , https://core.telegram.org/bots/api#inputrichblock , https://core.telegram.org/bots/api#inputrichblockdetails , https://core.telegram.org/bots/api-changelog . Проверить фактическую поддержку в текущей версии python-telegram-bot.

### 48. InputRichMessage

Метод `sendRichMessage`, аргумент `rich_message` — структура `InputRichMessage` с одним из трёх способов: `markdown` (Rich Markdown, НЕ MarkdownV2), `html` (Rich HTML), `blocks` (массив `InputRichBlock`). Ровно один способ. Для справки Poster рекомендуется **`blocks`** — явные разделы, раскрываемые блоки, надёжная структура. Не смешивать способы.

### 49. Основные блоки

- `InputRichBlockSectionHeading` — заголовки разделов.
- `InputRichBlockParagraph` — абзацы.
- `InputRichBlockList` — списки действий.
- `InputRichBlockDivider` — разделение крупных разделов.
- `InputRichBlockDetails` — раскрываемый блок (`type: "details"`, `summary`, `blocks`, опционально `is_open`) — ключевой для компактной справки.
- `InputRichBlockButtons` — только после проверки схемы; для простого возврата достаточно обычной InlineKeyboardMarkup через `reply_markup` в `sendRichMessage`. Декоративных кнопок без действий нет.

### 50. Техническая схема отправки

`sendRichMessage` с `chat_id`, `rich_message` (валидный `InputRichMessage`), `reply_markup` при необходимости. НЕ `sendMessage`. НЕ `sendRichMessageDraft`. Не использовать нейросеть для генерации содержимого справки во время запроса: справка статическая или собирается из текущего каталога текстов.

Если python-telegram-bot не поддерживает метод/классы — небольшой изолированный адаптер к официальному Bot API: существующий токен из конфигурации, без дублирования хранения токена, без вывода токена в логи, существующий жизненный цикл сетевого клиента если возможно, корректная обработка ошибок Telegram, возврат идентификатора отправленного сообщения, поддержка проверки ответа, покрытие тестами. Не создавать большую параллельную библиотеку Telegram. Не обновлять всё приложение до нестабильной версии SDK, если достаточно небольшого адаптера.

### 51. Содержание справки

Один структурированный Rich Message. Заголовок **Poster — помощь**. Введение: «Poster помогает создавать анонсы мероприятий по шаблонам, заполнять поля, добавлять фотографии и редактировать результат». Далее 10 разделов:

1. **Создание анонса** — нажать «Создать анонс»; выбрать площадку или личный шаблон; заполнить поля; добавить фото при необходимости; завершить; получить готовый анонс с редактором.
2. **Площадки** — что такое; как создать; какие поля обязательны; как изменить адрес и ссылку; как использовать для анонсов.
3. **Шаблоны** — что такое; личный и площадочный; как редактировать текст; для чего простой и расширенный варианты.
4. **Кирпичики** — что такое; как использовать `[код]`; системные и пользовательские; личные и локальные площадки.
5. **Дополнительные поля** — как заполняются; когда включается расширенный шаблон; как убрать доп. значение.
6. **Условные части** — просто: «Если поле не заполнено, можно автоматически скрывать связанную с ним часть шаблона — например, тире после времени начала или целую строку с ценой»; выбор кирпичика, выбор фрагмента, предпросмотр, сохранение. Без программных выражений.
7. **Фотографии** — добавить; удалить одну; удалить несколько; изменить фото готового анонса.
8. **Редактирование анонса** — где кнопки; как менять поля; как изменения отражаются в активном экземпляре; что происходит при повторном открытии.
9. **Управление площадкой** — шаблон; администратор; кирпичики; предложения; конфликты (с учётом модели полномочий).
10. **Команды** — краткий справочник реально существующих команд Poster. Не придумывать команды.

### 52. Дизайн

Главный заголовок; короткие абзацы; списки действий; раскрываемые разделы; ясное разделение тем; корректные ссылки; умеренно эмодзи. Ориентир — смартфон. При первом открытии видны заголовок, краткое описание и перечень свёрнутых тематических блоков. Раскрытие раздела не отправляет новое сообщение. Без бессмысленных таблиц и технической терминологии.

### 53. Навигация Rich Message

Справка — временный служебный экран. Открытие: зафиксировать экран-источник и его контекст; отправить Rich Message; корректно закрыть/заменить предыдущий служебный экран; не оставлять два конкурирующих меню. Возврат: восстановить предыдущий экран, страницу, поиск, фильтры; удалить временный Rich Message, когда возможно; не затронуть пользовательские анонсы; без лишней цепочки служебных сообщений. Если Rich Message нельзя редактировать выбранным механизмом — минимально необходимая замена. Проверить поддержку параметра `rich_message` у `editMessageText`; не предполагать произвольное преобразование типов сообщений.

### 54. Проверка

Тесты подтверждают: вызывается именно `sendRichMessage`; передаётся валидный `InputRichMessage`; корректная структура `blocks`; есть заголовки; есть реальные раскрываемые `InputRichBlockDetails`; все 10 разделов; нет обычного `sendMessage` под видом Rich Message; возврат восстанавливает исходный экран; временное сообщение справки удаляется корректно; остальные разделы не используют Rich Message. FakeBot различает `sendMessage` и `sendRichMessage`. Если возможно — дополнительная проверка реального Bot API в контролируемом тестовом чате. Ручное тестирование владельцем по умолчанию не требуется; непроверяемое автоматически отображение в клиенте — явно указать в отчёте.

## ЧАСТЬ XIV. НЕЗАВИСИМАЯ ПРИЁМКА

### 56. Правила тестирования

Tester проверяет утверждённое пользовательское поведение независимо от реализации: реальные обработчики, callback, состояние FSM, состояние БД, содержимое сообщений, Telegram entities, inline-клавиатуры, порядок вызовов Telegram API, количество создаваемых сообщений, удаление сообщений, правильный возврат. Недостаточно проверить одну функцию, если маршрут сломан.

### 57. Обязательные сценарии интерфейса

1. Главное меню → Управление → Площадки.
2. «Шаблоны» и «Кирпичики» в одной строке.
3. Создание площадки со всеми четырьмя полями.
4. Создание с пропущенными адресом и ссылкой.
5. Повторный вход в ранее заполненное необязательное поле.
6. Открытие единой административной карточки.
7. Скрытие пустых разделов предложений и конфликтов.

### 58. Обязательные сценарии сообщений

- **А. Без фото**: одна отправка полного анонса; клавиатура прямо под ним; нет «Анонс готов»; временный конструктор корректно закрыт.
- **Б. Одно фото**: один `sendPhoto`; полный caption; inline-кнопки; никаких дополнительных текстовых копий.
- **В. Медиагруппа**: один `sendMediaGroup`; полный текст в подписи альбома; одно отдельное служебное сообщение управления; нет отдельного сообщения с полным текстом; нет «Анонс готов».
- **Г. Слишком длинный текст**: публикация не выполняется; черновик сохранён; понятное ограничение; фото не теряются; после исправления возможно завершение.
- **Д. Редактирование**: анонс остаётся; открывается временный редактор; поле меняется; активный экземпляр обновляется; редактор закрывается; исторические экземпляры не меняются.
- **Е. Повторное открытие**: первый активен; второй успешно отправляется; первый без кнопок; второй с управлением; третье открытие снимает управление со второго; третий активен.
- **Ж. Старый callback**: не восстанавливает прежний экземпляр; не открывает редактор; не создаёт дубликаты; корректно отвечает на нажатие.
- **З. Удаление из БД**: запись удалена; исторические сообщения остались; старые кнопки не могут изменить удалённые данные.
- **И. Изменение количества фото**: 0→1; 1→2; 2→1; 1→0; несколько→0. Без ненужных сообщений и потерянных вложений.

### 59. Обязательные сценарии условных частей

Весь маршрут `Редактор шаблона → Условные части → Кирпичик → Фрагмент → Предпросмотр → Сохранение → Создание анонса → Рендер`: тире; скобки; полная строка; несколько условных частей; повторяющиеся кирпичики; одинаковые текстовые фрагменты; форматирование; гиперссылки; изменение исходного шаблона; копирование простого шаблона; расширенный шаблон с одним заполненным доп. полем; возврат к простому шаблону; сохранение после перезапуска.

### 60. Обязательные сценарии Rich Message

Настоящий вызов `sendRichMessage`; корректный `InputRichMessage`; реальные раскрываемые блоки; структура справки; кнопка возврата; очистка служебных сообщений; отсутствие Rich Message в других разделах.

### 61. Учёт сообщений

FakeBot фиксирует: `send_message`, `send_photo`, `send_media_group`, `send_rich_message`, `edit_message_text`, `edit_message_caption`, `edit_message_media`, `edit_message_reply_markup`, `delete_message`, `answer_callback_query`. Проверять не только итоговый текст, но и последовательность вызовов. Количество операций — часть UX-контракта. Отдельно проверять, что готовый анонс не удаляется вместе со служебным экраном.

## ЧАСТЬ XV. ПЛАН РАБОТЫ

- **Этап A — управление**: эмодзи 🧩; компактное меню; мастер площадки; динамическая карточка; локальные кирпичики; навигация. Целевые тесты и независимая проверка.
- **Этап B — списки и дата**: единый компонент пагинации; сохранение контекста; поиск и возврат; применение к спискам; формат даты. Целевые тесты.
- **Этап C — сообщения и анонсы**: самый ответственный UX-этап: удаление «Анонс готов»; цельные анонсы; inline-кнопки у одиночных сообщений; медиагруппы с отдельной панелью; временные редакторы; обновление активного экземпляра; архивные экземпляры без кнопок; защита старых callback; правильная очистка; редактирование фотографий. Перед сложными изменениями изучить текущее хранение Telegram message IDs и связи с draft/announcement; при необходимости Architect.
- **Этап D — условные части**: модель данных; миграция; интерфейс настройки; предпросмотр; валидаторы; рендер; правила изменения шаблона; поддержка entities; независимые сценарные тесты. Без скрытой эвристической обработки пунктуации.

Для каждого этапа: проверить затронутый код; зафиксировать точные критерии приёмки; выделить небольшие задачи; передать исполнителю; получить код и целевые тесты; независимая проверка; исправить дефекты; checkpoint и тематический коммит; перейти дальше. Полный `make check` — на границе релиза. Ручное тестирование владельцем по умолчанию не требуется.

## ЧАСТЬ XVI. РЕЛИЗ

### 68. Предрелизные проверки

Независимая приёмка A–E; полный `make check PYTHON=.venv/bin/python`; исправление блокирующих дефектов; тематические коммиты; push в `origin/main`; успешный CI. Не считать релиз завершённым, если CI не проверен либо тесты формально зелёные.

### 69. Бэкап и очистка тестовой БД

До первого публичного релиза все пользовательские данные — тестовые. После успешной проверки: штатно остановить Poster; создать проверенный WAL-aware backup; убедиться в пригодности копии; использовать штатный rebuild-механизм `db_maintenance.py`; не очищать БД ручным SQL; проверить актуальную структуру и миграции; системные кирпичики; стандартные шаблоны; нулевые пользовательские счётчики; сохранность конфигурации суперадминистратора; отсутствие SQLite-БД и резервных копий в Git. Не удалять существующие резервные копии автоматически. **Не удалять Telegram-сообщения и ранее отправленные анонсы при очистке БД.** Старые кнопки при отсутствии записей безопасно считаются недействительными.

### 70. Запуск службы

После обслуживания БД: запустить Poster штатно; проверить systemd user service; polling; логи; отсутствие restart-loop; отсутствие ошибок миграции и инициализации; готовность к использованию. Не публиковать секреты.

## 72. ИТОГОВЫЕ НЕПРИКОСНОВЕННЫЕ ТРЕБОВАНИЯ

1. Poster — приложение внутри Telegram, а не поток новых сообщений.
2. Служебные экраны преимущественно редактируются, а не отправляются заново.
3. После успешного ввода временные пользовательские сообщения очищаются; при ошибке — сохраняются.
4. Готовый анонс всегда цельный: текст вместе с фотографиями.
5. Один анонс с одной фотографией — одно Telegram-сообщение с подписью и кнопками.
6. Медиагруппа — цельный альбом с текстом в подписи; отдельно разрешена только служебная панель кнопок.
7. Готовый анонс не превращается в редактор; для редактирования — временный служебный экран.
8. Повторное открытие из «Мои анонсы» создаёт новый экземпляр; прежний — исторический снимок без кнопок.
9. «Назад» возвращает в действительный предыдущий контекст, сохраняя страницу, поиск и выбранный объект.
10. Условные части настраиваются через понятный интерфейс без программного синтаксиса.
11. Rich Messages — исключительно «Помощь», через настоящий официальный Telegram API.
12. Очистка тестовой БД не удаляет отправленные Telegram-анонсы.
13. Команда работает автономно, проводит независимые тесты и завершает релиз без бессмысленных промежуточных вопросов.
