# Лекало (Poster) — Telegram-бот конструктор анонсов

Бот-конструктор анонсов: автор выбирает площадку и шаблон, отвечает на
вопросы по кирпичикам, добавляет фотографии — и получает готовый анонс в
личном чате. Анонсы живут в **«📂 Мои анонсы»**: незавершённый анонс можно
продолжить, отправленный — открыть, исправить и переиздать.

Всё управление идёт через один постоянный экран: он перерисовывается на
месте, а не плодит сообщения. Данные пользователей хранятся локально в
одном файле SQLite; сеть нужна только для Telegram Bot API.

## Как это работает

```
Пользователь (личный чат)
  │  «📝 Создать анонс» — выбор площадки (личный шаблон — там же)
  │  (либо /new_wizard — экран выбора места)
  │  тап по площадке/шаблону сразу начинает анонс
  │  вопросы по кирпичикам (у каждого — подсказка типа и описание автора)
  │  дополнительные поля → фотографии («Без фотографий» или партия снимков)
  └──► последний ответ сам выдаёт готовый анонс в личный чат;
       правка из «📂 Мои анонсы» пересобирает и заменяет прошлую версию
```

* **Кирпичики вместо фиксированных полей** — состав анонса задаёт шаблон.
  У кирпичика есть **название** (видно в списках и на экране вопроса),
  **обозначение** (короткая вставка `[код]` в тексте шаблона) и
  необязательное **описание** — инструкция автору: что именно указать и в
  каком виде. Описание видно над полем ввода, в текст анонса не попадает.
* **Ответы проверяются по типу** (текст, число, дата, выбор и т.д.):
  неверный ввод возвращает тот же вопрос с объяснением, уже введённые
  значения сохраняются. Пропуск необязательного поля — не ошибка.
* **Превью идентично готовому анонсу**: живой блок и итоговый текст
  собираются одним кодом, поэтому шутки и подсказки интерфейса в анонс не
  попадают.
* **Черновики** пишутся в БД после каждого принятого изменения — анонс
  переживает выход из диалога и рестарт. Удалить может только пользователь,
  из списка, с подтверждением. Записи старше 30 суток удаляются
  автоматически раз в час (собственная `asyncio.Task`, без APScheduler).
* **Фото и альбомы**: после вопросов бот отдельно спрашивает фотографии;
  «Без фотографий» — такой же законный ответ. Набор больше лимита Telegram
  (10 снимков в медиа-группе) отправляется группами.
* **Ошибки не теряют данные**: сбой отправки или БД оставляет введённое в
  памяти и в черновике; прерванная отправка при повторе досылает только
  недостающую часть — без дублей.

## Разделы бота

| Раздел | Что внутри |
| --- | --- |
| «📝 Создать анонс» | выбор площадки/личного шаблона → кирпичики → доп. поля → фото → готовый анонс |
| «📂 Мои анонсы» | незавершённые и изданные анонсы: продолжить, открыть, править, удалить |
| «📍 Площадки» | справочник мест: поиск, карточки, создание, альтернативные названия |
| «🧩 Кирпичики» | личные типизированные поля: создание, карточка, правка, архив |
| «📝 Шаблоны» | личные и стандартные шаблоны площадок, секции, условные части, предпросмотр |
| «🛡 Администрирование» | кабинет администратора площадки и суперадминистратора, передача прав |
| «❓ Помощь», «ℹ️ О проекте» | Rich Message со справкой и сведениями о проекте |

**Роли.** Суперадминистратор задаётся в `.env` (`SUPERADMIN_USER_IDS`).
Администратор площадки назначается суперадминистратором и может передать
роль другому пользователю: одноразовая ссылка, 24 часа, двустороннее
подтверждение, в БД хранится только SHA-256 токена.

**Предложения кирпичиков.** Личный кирпичик можно предложить площадке или
всей системе; действующий администратор площадки/суперадминистратор
одобряет или отклоняет. Одобрение транзакционно создаёт отдельный
кирпичик с неизменяемым снимком исходного.

## Стек

* Python 3.13+ (проверено на Python 3.14),
  [python-telegram-bot](https://python-telegram-bot.org) 21–22
  (асинхронный API, `ConversationHandler`; проверено на 22.8).
  `JobQueue` отключён явно (`job_queue(None)`): APScheduler не требуется.
* SQLAlchemy 2.0 (typed `Mapped[]`), SQLite (WAL, busy timeout,
  `foreign_keys=ON`).
* PyYAML — каталоги текстов интерфейса и фраз юмора.
* Развёртывание: локально или Docker (`Dockerfile`, `docker-compose.yml`).
* Качество: ruff, black, mypy, `unittest` (без внешних сервисов).

## Быстрый старт (локально)

```bash
cd Poster
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pip install -r requirements-dev.txt   # для make check (опционально)

cp .env.example .env       # и заполнить TELEGRAM_BOT_TOKEN (секрет в git не попадает)

python bot.py              # или: make run PYTHON=.venv/bin/python
```

Для фонового запуска на сервере есть `botctl.sh`:

```bash
./botctl.sh start      # nohup, PID в logs/post_bot.pid
./botctl.sh status
./botctl.sh stop       # SIGTERM, как Ctrl+C
./botctl.sh restart
```

Ctrl+C (или `stop`) прерывает polling; все данные остаются в SQLite —
досохранять вручную нечего.

## Конфигурация (`.env`)

Полное описание каждой переменной — в [.env.example](.env.example).
Обязательна только `TELEGRAM_BOT_TOKEN`.

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | токен от @BotFather (обязательно) |
| `DATABASE_URL` | строка подключения к SQLite; по умолчанию `post_bot.db` в каталоге `Poster/` |
| `LOG_LEVEL` | `DEBUG`/`INFO`/`WARNING`/`ERROR`, по умолчанию `INFO` |
| `SUPERADMIN_USER_IDS` | постоянные Telegram user ID суперадминистраторов через запятую |
| `SUPERADMIN_CONTACT_URL` | http(s)-ссылка на контакт суперадминистратора для кнопки «Я админ места» |
| `UI_HUMOR_ENABLED` | выключатель редких шутливых вариаций (`0`/`false`/`no`/`off`/`нет`/`выкл`) |
| `HUMOR_PHRASES_PATH` | путь к каталогу фраз юмора (по умолчанию `config/humor_phrases.yaml`) |

Бот работает в личном чате: ID чатов не нужны.

* `.env` не коммитится и не публикуется; в git — только `.env.example` без
  значений;
* токен не пишется в логи: уровень httpx принудительно `WARNING`, а сам
  токен вычищается из сообщений и трассировок (`SecretScrubFilter`).

## База данных

* Рабочая база — **`Poster/post_bot.db`**, путь привязан к каталогу модуля,
  а не к рабочей директории: запуск из `Poster/`, из корня репозитория, из
  IDE или из systemd использует один и тот же файл.
* Путь можно переопределить `DATABASE_URL` (в Docker —
  `sqlite:////app/data/post_bot.db`).
* При подключении выставляются `journal_mode=WAL`, `synchronous=NORMAL`,
  `foreign_keys=ON` и busy timeout — обработчики работают параллельно, а
  внешние ключи проверяет SQLite.
* Схема создаётся **единой базовой версией 1.0.0** (`migrations.py`):
  31 таблица с индексами, CHECK, FK и 45 триггерами плюс каталог системных
  кирпичиков. Журнал `schema_migrations` хранит версию и контрольную сумму
  DDL; повторный запуск ничего не применяет заново.
* Перед первым ожидающим DDL существующей непустой базы автоматически
  создаётся WAL-aware копия (SQLite Backup API + `integrity_check`, права
  `0600`). Сбой копии отменяет миграцию, база остаётся нетронутой.
* Новые изменения схемы — только новой записью `Migration` с `version=2` и
  далее. Подробности и runbook — [docs/migrations.md](docs/migrations.md).

### Резервная копия

Автоматическая копия — страховка механизма, а не замена эксплуатационному
backup. Перед выкаткой версии с миграцией рекомендуются остановка бота и
отдельная копия:

```bash
cd Poster
# 1. остановить бота (Ctrl+C / ./botctl.sh stop) и убедиться, что процесс завершён
# 2. дополнительная копия — все файлы базы:
cp post_bot.db* /путь/к/копии/
# восстановление: бот остановлен → вернуть файлы на место
```

Штатное обслуживание рабочей базы — только через `db_maintenance.py`:

```bash
make db-maintain-report              # целостность + проверенный WAL-бэкап + счётчики
make db-maintain-clean               # полный rebuild-цикл (релизная очистка)
make db-maintain-clean DB=/tmp/test.db
```

## Проверки

```bash
pip install -r requirements-dev.txt
make check          # ruff + black + mypy + все тесты (он же make accept)
```

`make check` выполняется полностью локально, без живого Telegram, токена и
рабочей базы: unit- и интеграционные тесты идут через настоящий
`Application.process_update` поверх FakeBot и временной SQLite, плюс
smoke-запуск `bot.main()` с фиктивным токеном и заблокированной сетью.
Сейчас это **3300+ тестов**.

По отдельности (из каталога `Poster`):

```bash
ruff check .
black --check .
mypy .
python -W ignore::DeprecationWarning -m unittest discover -s tests
make format        # автоформатирование (black + ruff --fix)
make test          # только тесты
```

### Автоматические проверки (GitHub Actions)

Каждый push в `main` и каждый Pull Request проверяются workflow
[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) на Python 3.13 и
3.14 (`make check` + `workflow_dispatch` для ручного запуска). Секреты и
Telegram не нужны: `tests/__init__.py` подставляет фиктивный токен, сеть
заблокирована, базы временные.

## Команды бота

| Команда | Назначение |
| --- | --- |
| `/start` | главное меню (экран обновляется на месте) |
| `/new_wizard` | создание анонса: площадка/шаблон → кирпичики → фото |
| `/drafts` | «📂 Мои анонсы»: незавершённые и история |
| `/places` | справочник площадок |
| `/bricks` | личные кирпичики |
| `/templates` | личные шаблоны |
| `/admin` | кабинет администратора (виден только при правах) |
| `/report` | сообщить о проблеме |
| `/help` | справка |
| `/cancel` | отменить текущий диалог (данные сохраняются) |

Команды, отправленные во время создания или редактирования анонса,
сохраняют незавершённый анонс и завершают диалог.

## Логи

* Все логи — в **`Poster/logs/bot.log`**, путь привязан к каталогу проекта.
* Ротация: активный файл до **5 МБ**, до **5 архивов** (`bot.log.1` …
  `bot.log.5`); Unicode переживает границу ротации.
* Уровень — `LOG_LEVEL` (по умолчанию `INFO`); логи идут и в консоль.
* Токен вычищается из сообщений и трассировок (`SecretScrubFilter`) даже при
  `LOG_LEVEL=DEBUG`; полный текст пользовательского ввода в логи не
  пишется — только событие, поле и длина.
